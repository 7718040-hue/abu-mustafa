# نسخة Cloudflare المستقلة — 8 أكتوبر 2026

هذه النسخة تعمل على **Cloudflare Workers مع Static Assets + D1 + R2 + Access**. هي فرع مستقل عن نسخة Sites. لا تختَر Pages لرفع مجلد HTML فقط؛ لن يعمل ذلك كبديل كامل لخدمة الإدارة الحالية.

## ما تم تجهيزه

- المتجر العربي والصور والخطوط المحلية ولوحة التحكم والتعليمات داخل الأقسام.
- صفحات المنتجات والأقسام والمنشورات الحية، وواجهات الإدارة، والصلاحيات، ومراجعة التقييمات.
- تحقق خادمي من توقيع Cloudflare Access ومن المرسل والجمهور ومدة الصلاحية. حذف ترويسات هوية Sites القادمة من الزائر.
- رابط الموقع قابل للضبط عند البناء؛ يتغير معه canonical وخريطة الموقع والبيانات المنظمة وروابط الاستفسار.
- الموارد DB وBUCKET وASSETS معلنة في wrangler.json. تمر الطلبات عبر Worker أولًا حتى لا تحجب ملفات HTML قديمة تغييرات الإدارة.
- الفهرسة مغلقة في النسخة التجريبية، ولا يوجد نشر تلقائي أو اتصال بحساب Cloudflare ضمن هذه النسخة.

## 1. تثبيت النسخة واختبارها

استخدم Node 22.13 أو أحدث، ويفضل Node 24، ثم:

~~~sh
npm ci
npm test
npm run build
~~~

الاختبارات تستعمل قواعد وصورًا مؤقتة وتوقيعات اختبار. لا تكتب في قاعدة الموقع الحالي. لا ترفع مجلدات node_modules أو .wrangler أو .dev.vars أو النسخ الاحتياطية إلى GitHub.

## 2. إنشاء موارد مستقلة في حساب المالك

~~~sh
npx wrangler login
npx wrangler d1 create abu-mustafa-cloudflare-catalog
npx wrangler r2 bucket create abu-mustafa-cloudflare-photos
~~~

ضع database_id الناتج في wrangler.json بدل REPLACE_WITH_NEW_D1_DATABASE_ID. استخدم قاعدة وحاوية جديدتين. لا توجّه هذه النسخة إلى موارد Sites الحالية.

طبّق الترحيلات على القاعدة الجديدة:

~~~sh
npm run db:migrate:remote
~~~

إذا أردت نسخة مطابقة للبيانات الحالية، انقلها في الخطوة الخامسة **قبل فتح الموقع أو دخول الإدارة لأول مرة**. إن لم تنقلها، يستورد الموقع سجلات المنتجات الأولية الـ35 والأسئلة الأولية فقط؛ لا يستورد التقييمات والمنشورات والتعديلات والصور المرفوعة الموجودة في Sites تلقائيًا.

## 3. اختيار رابط النسخة

اسم Worker المقترح abu-mustafa-cloudflare. رابط workers.dev يتكون من اسم Worker والنطاق الفرعي الفعلي لحساب المالك. احصل على النطاق الفرعي من لوحة Cloudflare ثم ضع رابط HTTPS الصحيح في vars.PUBLIC_ORIGIN داخل wrangler.json.

لا تستعمل رابط الموقع الأصلي أو cloudflare-preview.example في الإنتاج. إذا أضفت نطاقًا خاصًا لاحقًا، حدّث PUBLIC_ORIGIN وأعد البناء واضبط Access على النطاق الجديد. أبقِ preview_urls=false كي لا توجد روابط معاينة إضافية تحتاج حماية مختلفة.

## 4. حماية الإدارة وتعيين المالك

من Zero Trust → Access → Applications أضف تطبيق Self-hosted على **الرابط نفسه** وبمسارات الإدارة فقط. أضف المسارات التالية في التطبيق نفسه حتى تشترك في Audience واحد:

- /admin
- /admin/*
- /api/admin
- /api/admin/*

اترك صفحات المتجر العامة خارج التطبيق. أضف سياسة Allow بالبريد الفعلي للمالك، وبريد المشرف أو المحرر عند الحاجة. لا تستخدم سياسة Bypass أو Everyone. يمكن اختيار رمز بريد مؤقت One-time PIN كوسيلة دخول.

من إعدادات التطبيق انسخ Application Audience (AUD)، ومن إعدادات Zero Trust انسخ نطاق الفريق مثل https://TEAM.cloudflareaccess.com. ضعهما في ACCESS_AUD وACCESS_TEAM_DOMAIN داخل wrangler.json. لا تضف مسارًا إلى نطاق الفريق.

اضبط بريد المالك سرًا عبر:

~~~sh
npx wrangler secret put SITE_OWNER_EMAIL
~~~

اكتب البريد الذي سيسجل الدخول فعليًا، وليس البريد الظاهر للزوار إلا إذا كان هو حساب المالك. لا تحفظ قيمة السر في المستودع. أول دخول موثّق بهذا البريد يربط الإدارة بالهوية الثابتة في Access. إضافة موظف تحتاج السماح ببريده في Access ثم تعيين دوره داخل لوحة الموقع؛ السماح في Access وحده لا يمنحه صلاحية التحرير.

لا تشغّل معاينة الإدارة بترويسات مزيفة أو LOCAL_ADMIN_PREVIEW. تحتاج المصادقة الحقيقية إعداد حساب Access؛ الاختبارات المحلية تتحقق من هذه الحدود باستعمال مفاتيح مؤقتة معزولة.

## 5. نقل البيانات والصور الحالية اختياريًا

تصدير بيانات الإدارة من زر اللوحة ملف كتالوج، ولا يحتوي وحده على جداول D1 كاملة أو ملفات الصور. للحصول على نسخة مطابقة اجمع لقطة كاملة للجداول والصور وفق docs/cloudflare-transfer.md. احتفظ بها خارج GitHub لأنها قد تحتوي بيانات العملاء والمسودات.

## 6. فحص الإعداد والنشر بعد الموافقة

~~~sh
npm run deploy:check
npm run deploy
~~~

الفحص الأول يرفض القيم النموذجية. لا يثبت وجود الموارد أو صحة سياسة Access عن بعد؛ راجعها في الحساب. النشر لم يُنفَّذ أثناء تجهيز هذا الفرع.

لربط تحديثات GitHub لاحقًا: من Workers & Pages أنشئ Worker مرتبطًا بالمستودع 7718040-hue/abu-mustafa واختر فرع cloudflare-hosting. أمر البناء npm run build، وأمر النشر npm run deploy. اضبط إعدادات حساب Cloudflare أولًا. لا تربطه بفرع main. تحديث الكود لا ينقل بيانات D1 أو ملفات R2.

## 7. الاختبار على الرابط الحقيقي قبل اعتماد النسخة

1. الرئيسية والمنتجات والأقسام والمنشورات والصور والروابط وأرقام الاتصال وواتساب والخريطة من الهاتف.
2. افتح الإدارة في نافذة خاصة: يجب أن يطلب Access الدخول؛ وفي حساب غير مسموح يجب أن يرفضه.
3. جرّب دخول المالك، وحفظ عنصر تجريبي وإخفاءه واستعادته، ورفع صورة، وإضافة مسودة ونشرها، والتقييمات وتعليمات الأقسام.
4. جرّب محررًا لا يستطيع إدارة الفريق أو الأقسام أو نشر مسودة، ثم اسحب صلاحيته وتأكد من رفض دخوله.
5. حدّث الكود ثم تأكد من بقاء البيانات والصور. راجع حدود الخطة المجانية والاستهلاك في الحساب.
6. اترك PUBLIC_INDEXING=disabled أثناء المقارنة. بعد اعتماد الرابط النهائي يمكن وضع enabled-after-owner-approval. افحص robots.txt وsitemap.xml وcanonical والبيانات المنظمة. يلزم تحقق Search Console جديد؛ الملف القديم لا يُستخدم على هذه النسخة. إتاحة الزحف لا تعني أن جوجل فهرس كل الصفحات.

## حدود التسليم

اجتياز الاختبارات المحلية وتجهيز الفرع لا يثبت تشغيل النسخة داخل حساب Cloudflare. التشغيل الفعلي يحتاج موارد الحساب وAccess والمالك ونقل البيانات بحسب الحاجة، ثم اختبار الرابط الحقيقي. لا يوجد ضمان مطلق بعدم ظهور خطأ؛ الاختبارات تقلل المخاطر وتحدد ما تحقق فعليًا.

المراجع الرسمية: [إعداد Workers](https://developers.cloudflare.com/workers/wrangler/configuration/)، [Access لحماية Worker أو مسار](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)، [التحقق من JWT](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).
